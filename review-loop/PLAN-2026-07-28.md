# review-loop Tier & Roster Upgrade — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **ALSO REQUIRED:** every task that edits skill prose follows superpowers:writing-skills — RED baseline before writing, GREEN verify after. "Test" here means a pressure-scenario fixture run against a subagent, not pytest.

**Goal:** Make review-loop's roster adaptive and its cost proportionate — an effort tier derived from complexity × risk, a staffing predicate that earns each specialist, per-round re-inventory with decay, and a reviewer contract that covers absence-defined defects.

**Architecture:** All rules land inside the skill's existing forced artifacts (SCOPE seal, ROSTER, LEDGER, FIX MANIFEST, CLOSE rollup) rather than as new prose checklists — an executor that must fill a field cannot skip the rule it encodes. The tier is derived by the existing risk-inventory subagent (now run ≥2× from a config roster), combined mechanically by the orchestrator, and printed in the report. No new stage is added to the loop.

**Tech Stack:** Markdown skill documents; pressure-scenario fixtures under
`tests/`; subagent dispatch for reviewers/raters/adjudicator; optional
external reviewer CLIs. `multi-review` (`~/kramtime/multi-review`) is a
future integration gated by Task 7's prerequisites.

## Global Constraints

- Repo root: `~/kramtime/llm-skillbook` (git repository, branch `main`, initialised 2026-07-28 — see Task 0). **Two path conventions, both live:** each task's **Files** block and every `grep` are relative to `review-loop/` (the `cd` in each command establishes it); every `git add` / `git commit` runs from the repo root and therefore names `review-loop/<file>`. Both appear as written throughout — this is the convention, not a slip.
- Distillation rule (user, standing): do not bloat the skill. Rules become forced artifact fields, never prose lists. If an addition can be expressed as a field an executor must fill, express it that way.
- Ladder is exactly `low | med | high | max`. No other tier vocabulary anywhere in the docs.
- The tier may control effort **spent** (staffing threshold, round cap, reviewer model tier). It must never control what counts as **done** — `settled`, CONVERGED, merge-readiness, and the existence of the adjudication pass are tier-invariant.
- **The honest form of that claim:** the verdict *rules* are tier-invariant; the verdict *outcome* is invariant only given the same findings and the same verification quality. A cheaper tier staffs fewer areas (fewer findings, fewer rows) and audits fixes with less capable reviewers (`SKILL.md:168-173` — FIX_VERIFIED requires every reviewer's `FIX-AUDIT` line to read clean, and a weaker reviewer writes "clean" more readily). Neither is preventable; both are disclosable. Wherever the plan states the invariant, it states this qualification with it. A rule that overclaims is a rule a future editor will trust past its warrant.
- The knob gates **staffing**, never **naming**. Every inventory area is named; areas that do not earn a specialist get an explicit `Not staffed: <area> — <reason>` line. That exact field name is used everywhere — no paraphrases.
- Every rating, derivation, and staffing decision is printed in the final report with its evidence, so a run's cost is auditable after the fact.
- Two rating vocabularies exist and must never be conflated: **`CONSEQUENCE`** is `Critical | Important | Minor` (per inventory area, drives the staffing threshold) and **`R`** is `low | med | high | max` (per rater, drives the combiner). There is no mapping between them — `R` is rated directly on its own anchors, and the highest `CONSEQUENCE` in the inventory serves as `R`'s cited *evidence*, never as its value.
- **Ground truth is frozen before RED runs.** Every task's step order is: write SCENARIO → write GROUND-TRUTH (defects, scoring ladder, RED bar) → run RED → write the rule → run GREEN. Authoring the ladder after seeing RED output is retro-fitting, which is exactly what the next constraint forbids; a plan that orders the steps the other way invites it. Where the numbering below shows GROUND-TRUTH after the RED run, the numbering is wrong and this constraint governs.
- **A RED must fail somewhere in the supported executor range.** Each fixture
  pre-commits its RED bar before dispatch. At least one supported executor
  must cross that failure bar; a stronger executor's pass is a useful negative
  control, not proof the rule is unnecessary (the existing S3 baseline is
  sonnet 2 / haiku 0). Require both tiers to RED only when the claim itself is
  capability-invariant. If every supported executor passes, strengthen the
  fixture or drop/re-scope the rule — never retro-fit the ladder.
- Prose edits are twin-prone: rounds 7–8 of this skill's own self-review produced three TWIN MISSES (a fixed primary statement with an unfixed sibling in another file). Every prose task runs a named twin search across `SKILL.md`, `reviewer-addendum.md`, `dispatch.md`, `DESIGN.md`, `README.md` and records the pattern + hit count.
- **Fixture executor tiers apply to judgement cells only.** A cell whose pass rule depends on what a model concluded runs at sonnet and haiku, matching `tests/baseline/RESULTS.md` convention, scored 0–2 per the scenario's ground-truth ladder, rationalizations captured verbatim. A cell whose oracle is a parse, an exit status, a dispatch argument, or a file hash is *deterministic*: model capability cannot change its outcome, so it runs once, records `Executors: deterministic — n/a`, and passes or fails on the assertion rather than a score. The RED-bar rule below is defined over the supported executor range and therefore binds judgement cells; a deterministic cell REDs by failing its assertion against the pre-edit skill.
- **Every scenario pins the EFFORT TIER it runs under.** Staffing-dependent expectations invert across tiers: Task 3's ground truth scores 2 only when shallow areas are *unstaffed*, but at `max` the rule is that every named area is staffed, so the correct answer flips. Task 6's decay expectations are tier-sensitive the same way. Pin `TIER: <low|med|high|max>` in the scenario header — unpinned, a fixture silently grades against the wrong rule when Task 10 re-runs it as a regression suite. `TIER: N/A` is a legitimate value, for reviewer-side fixtures and anything whose behaviour the ladder does not touch. This binds the scenarios **this plan writes**; the three pre-existing fixture directories predate the ladder and are covered instead by Task 10's manifest, which records their real envelopes rather than assuming this one.
- One negative fixture deliberately tests omission of the invocation tier.
  It records `TIER-INPUT: ABSENT` (an envelope condition, **not** a fifth
  ladder value) plus its phase-specific expected behavior. No other new
  fixture may omit `TIER`.
- **Every fixture states and preserves its production-equivalent prompt
  envelope** — the exact document set, substitution map, resolved bracket
  choices, and fully rendered prompt dispatched. Not "dispatch with the
  current skill": name the files and render recipe. Store the raw response,
  resolved executor/model, timestamp, score, and scorer rationale beside the
  result. This is outcome-determining for Task 7, whose rules land in
  `dispatch.md`, and for Task 5, which needs `raters.md`.
- **The executor under test never receives the answer key.** Ground truth
  lives in `GROUND-TRUTH.md` beside the scenario and is not part of any
  rendered prompt. Prefer a tool-less executor wherever the fixture does not
  test search behaviour — that removes the question entirely. Where the
  fixture needs tools, stage the rendered prompt and declared subject/context
  files in a scratch directory and run there. If the executor could still
  reach this repository, record that in `RESULTS.md` rather than claiming an
  isolation the host does not enforce; a fixture whose result depends on the
  executor *not* having looked is weak evidence, and saying so is the fix.
- RED baseline for every fixture is the **current** skill (pre-edit), not the pre-skill draft — the question is whether today's skill already prevents the failure.
- **Fixture pass rules are per-scenario, not “maximum score everywhere.”**
  The manifest records the mandatory behaviours, accepted score/pass rule,
  and frozen baseline for every cell. A surprising pass or threshold-crossing
  failure gets two confirmation reruns; ordinary cells stay one run per
  executor so the suite remains proportionate.
- **Rater/adjudicator config is trusted input from outside the sealed tree.**
  It is read from a user-owned path outside the reviewed repository, or
  supplied inline at invocation. A config file found *inside* the reviewed
  repository is subject material: never auto-loaded and never executed, under
  `--force` or otherwise. A rater or reviewer CLI command is a per-invocation
  user authorization — never discovered from the repository. It runs from an
  out-of-tree cwd and must not write the sealed tree. That is the whole
  boundary: this is a skill that dispatches agents, not a build system
  executing untrusted toolchains, and a heavier control-plane story here buys
  protection against a threat the loop does not have.
- **Every fixture cell has a stable ID and a manifest row.** The manifest is
  one row per cell, not one per directory, and records the runner command,
  envelope, tier, oracle, pass rule, and raw-evidence path. The suite fails
  closed when a declared cell has no manifest row.
- **Every fixture records what it ran against.** `RESULTS.md` for each cell
  carries `INPUTS-SHA` — the commit of the *test-input* tree (operative
  documents, harness, scenarios, ground truths, render maps, manifest), taken
  before the run and excluding the result files the run is about to write —
  plus the fully rendered prompt, the raw response, the resolved
  executor/model, timestamp, score, and scorer rationale. Reproducing a result
  means checking out that SHA and re-running the recorded command. Naming the
  whole tree instead would be self-defeating: writing the results changes it.

- [ ] **Step 1: Write the renderer**

Create `tests/harness/render-reviewer.sh`:

```bash
#!/usr/bin/env bash
# Render a reviewer prompt exactly as the dispatcher sends it.
#
# Usage: tests/harness/render-reviewer.sh MAPFILE [OMIT-SECTION ...]
#   MAPFILE      lines of "key<TAB>value"; a value of "@path" is replaced by
#                that file's contents. One line per {{ placeholder }}, plus a
#                mandatory "base_template" line (see below).
#   OMIT-SECTION exact "## " heading text to drop, e.g. "This round".
#
# Emits the rendered prompt on stdout and nothing else. Callers dispatch
# those exact bytes and store them beside the result.
set -euo pipefail

here=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)
addendum="$here/../../reviewer-addendum.md"
map=${1:?usage: render-reviewer.sh MAPFILE [OMIT-SECTION ...]}
shift

# 0. The addendum is appended to a base template when one is available, and
#    is the whole prompt when one is not. Both are real production paths, so
#    the map must say which this fixture tests rather than let the renderer
#    pick: "base_template<TAB>@path" or "base_template<TAB>none".
base_spec=$(awk -F'\t' '$1=="base_template"{print $2; exit}' "$map")
case ${base_spec:-} in
  none) base="" ;;
  @*)   base=$(cat "${base_spec#@}") ;;
  *)    echo "render: map must set base_template to @path or none" >&2; exit 1 ;;
esac

# 1. The prompt is the fenced block; prose outside it addresses the
#    dispatcher, not the reviewer. Step 0 of this task moved every
#    reviewer-directed rule inside that fence, so this is the whole contract.
body=$(awk '/^```$/{f=!f; next} f' "$addendum")
[ -n "$body" ] || { echo "render: no fenced prompt block in $addendum" >&2; exit 1; }
grep -q '^## Ground rules' <<<"$body" || {
  echo "render: fenced block is missing the Ground rules section" >&2; exit 1; }

# 2. Drop the conditional sections named on argv.
for section in "$@"; do
  body=$(awk -v s="## $section" '
    $0 ~ "^"s"([[:space:]]|$)" {skip=1; next}
    /^## / {skip=0}
    !skip' <<<"$body")
done

# 3. Resolve away the trailing [choice | menu] annotations, as the
#    dispatcher does.
body=$(sed 's/[[:space:]]*\[[^][]*\][[:space:]]*$//' <<<"$body")

# 4. No menu may survive into a dispatched prompt.
if grep -n '\[[^][]*|' <<<"$body"; then
  echo "render: unresolved menu above" >&2; exit 1
fi

# 5. Substitute. Values carry diffs and code, so pass them through the
#    environment rather than a sed replacement string.
while IFS=$'\t' read -r key value; do
  [ -n "$key" ] && [ "$key" != base_template ] || continue
  case $value in @*) value=$(cat "${value#@}") ;; esac
  body=$(VAL="$value" KEY="$key" perl -0pe \
    's/\{\{\s*\Q$ENV{KEY}\E\s*\}\}/$ENV{VAL}/g' <<<"$body")
done < "$map"

# 6. Fail closed on any placeholder the map did not fill.
if grep -n '{{' <<<"$body"; then
  echo "render: unfilled placeholder above" >&2; exit 1
fi

[ -z "$base" ] || printf '%s\n\n' "$base"
printf '%s\n' "$body"
```

# Absence clause — ground truth & scoring (NEVER shown to agents under test)

Three planted defects, one per clause bullet, none visible in the added
lines:

- **D1 (deleted guard)**: the `EmptyOrderError` throw was removed. An empty
  order now yields a zero-total invoice that `nightly.ts` merely warns about
  and emails to the customer. The invariant "an invoice always has line
  items" is gone and re-established nowhere.
- **D2 (orphaned caller)**: `src/api/preview.ts` catches `EmptyOrderError`.
  With the throw site deleted that branch is dead, and an empty order now
  returns a 200 with a zero-total invoice instead of a 400.
- **D3 (enclosing scope)**: `computeTax` is a function this diff changes —
  the second hunk adds `exempt` to its signature and an early return. The
  hunk's own last line, `return base * RATES[region]`, is **unchanged**;
  the enclosing-scope obligation is what puts it in scope. `RATES` is typed

  therefore `total` — is `NaN`. The failing input is provable from the
  excerpt: `region: 'de'`. A reviewer reading only the added lines sees a
  correctly-defaulted parameter and stops. Tests the third bullet, which no
  other defect here covers.

The signature change to `computeTax` is a decoy: correct, defaulted, safe.
A review that reports only the decoy has missed the diff's actual damage.

## Scoring
- **0**: reports none of D1–D3. (Reporting only the decoy scores 0.)
- **1**: reports one.
- **2**: reports D3 **and** at least one of D1/D2, naming the removed
  invariant for D1 or the affected call site for D2. D3 is mandatory because
  it is the only plant that exercises the enclosing-scope obligation.

**RED bar: ≤ 1 in at least one supported tier.** The scenario's own curation is a tell — it
hands the reviewer `preview.ts` under a heading — so expect RED at 1 (D1

````markdown
# Rater configuration

Raters skim the sealed scope and return the risk-surface inventory plus a
complexity rating. Their output always derives a candidate EFFORT TIER; a
user-passed tier overrides that candidate without suppressing the rating or
inventory.

**At least two raters run, from different vendors where available.** The
derivation is the highest-leverage step in the loop; a single rater's
miss compounds through staffing, rounds, and model choice for every
subsequent round. Two independent inventories also give free double
coverage of the risk surface itself.

**What two raters actually buy, stated honestly.** Across different
vendors, this is genuine independence: different training, different
blind spots. In a subagent-only environment — the default dispatch path —
two raters are two samples of one model. That reduces sampling variance
and catches careless reads; it does **not** defend against a systematic,
model-shaped blind spot, and nobody should believe it does. The cost is
paid on every run, including runs that turn out to be `low`, because the
tier is unknown until rating completes. Worth it for the variance
reduction alone; do not oversell it.

Raters are listed in the user-owned, out-of-tree config
`${XDG_CONFIG_HOME:-$HOME/.config}/review-loop/raters.yaml` by default; an
invocation may pass an explicit absolute config path outside the sealed tree,
which takes
precedence. A config found inside the reviewed repository is inert subject
data: never auto-loaded, never executed. Resolve symlinks before reading and
require the final file to sit outside the seal — that check is what stops an
in-tree config from being loaded under another name. A `kind: cli` rater runs
its configured command from an out-of-tree cwd and may not write the sealed
tree; the command itself is the user's per-invocation authorization, on the
same footing as the reviewer CLI that `SKILL.md:134` already accepts. If
neither trusted source exists, **ask** — never invent a rater command,
exactly as that line already requires. Non-interactive execution must pass an
explicit config path, or a complete inline override naming at least two
raters and an adjudicator. The override includes `model_tiers` iff any
configured or invoked component is a subagent. `--force` neither trusts an
in-tree config nor invents missing components; with no usable config it
records `NOT STARTED — RATING CONFIG ABSENT` and dispatches nothing.

`--force` bypasses only the enumerated operational confirmation gates:
the prompt to provide rater config (by failing visibly when none was
provided) and a roster above eight.
It never supplies finding authority, accepts risk, waives evidence, resolves
a ledger row, changes CLOSE, or answers a user decision required by
adjudication.

Each entry declares how it is dispatched, because "claude" alone does not
say whether to spawn a subagent or shell out, and the two have different
failure modes:

```yaml
# review-loop-raters.yaml
raters:
  - name: claude
    kind: subagent            # subagent | cli
    model: most capable       # relative tier, resolved at dispatch; never a model ID
  - name: codex
    kind: cli
    command: codex exec --model gpt-5-codex   # user's own command, run as given
  - name: kimi
    kind: cli
    command: kimi review --stdin

fallbacks:                    # replacements; still need two usable ratings
  - name: backup-subagent
    kind: subagent
    model: most capable

adjudicator:                  # per-round adjudication pass
  kind: subagent
  model: most capable

model_tiers:                 # required host-specific resolution
  mid-tier: <supported subagent model value>
  one above mid: <supported subagent model value>
  most capable: <supported subagent model value>
```

**Field meanings, so nothing is left to inference.** `kind: subagent`
dispatches in-session and `model` names a *relative* tier from the EFFORT
TIER vocabulary (`mid-tier`, `one above mid`, `most capable`) — never a
model ID, per the no-hardcoded-models rule. `kind: cli` runs its `command`
from an out-of-tree cwd, receiving the scope on stdin — the user wrote that
command, exactly as they already do for reviewer CLIs. The vendor picks the
model, so `model` is ignored and what actually ran is recorded from the CLI's
own report. A failed or unparseable rater is retried once. If fewer than two
usable ratings remain, dispatch a configured fallback as a **replacement**
and merge it with the surviving rating. If two usable ratings still cannot
be produced, stop Stage 0 and ask; under `--force`, close as
`NOT STARTED — RATING INDETERMINATE`. Never derive from one. The same
two-output floor and retry/replacement rules govern the per-round inventory
refresh, where falling short makes the round INDETERMINATE instead (Task 6).

`most capable` is the default for **Stage 0's** raters and for the
adjudicator, and deliberately not on the effort ladder. Both are decisions
whose errors compound across staffing and disposition, and both are cheap in
absolute terms: full C/R rating runs once per run, adjudication once per
round.

**The per-round inventory refresh does not inherit that default.** It runs
its raters at the run's own EFFORT TIER reviewer model. Applying `most
capable` there is what breaks cost-proportionality: at `low` the roster is
two mid-tier reviewers and nothing else, so two most-capable raters *per
round* would cost more than the review they scope and invert the tier's
entire point. Refresh raters are also answering a much smaller question —
"what moved in the risk surface since last round?", against a merged
inventory that already has two independent Stage 0 raters behind it — and

## Component dispatch protocol

Rater and adjudicator calls use the same transport envelope regardless of
vendor:

- write a fully rendered prompt to a fresh out-of-tree file and feed its
  bytes on stdin to a `kind: cli` command; capture stdout verbatim to a
  fresh authoritative report file and stderr separately as diagnostics;
- a `kind: subagent` receives the same rendered prompt and its final returned
  message is the authoritative report (persisted verbatim out of tree);
- raters and adjudicators are dispatched with `Read`, `Grep`, `Glob` and no
  `Write`/`Edit`/`Bash`. They read the scope and emit a judgement; nothing in
  their contract asks them to run anything, so execution is capability they
  have no use for. **Reviewers are the deliberate exception** — Task 7 gives
  them `Bash` because "Tests in scope" obliges them to run the suite and
  prove a test bites. Do not harmonize these two profiles; the difference is
  the contract, not an oversight;
- require the host call/CLI to finish successfully before its deadline and
  require the authoritative report to parse. CLI success is exit 0;
  subagent success is host status `completed` plus a delivered final response.
  No other status maps to success. After the no-progress threshold, ping once;
  if still idle/failed/cancelled, interrupt through the host and retry with a
  fresh agent/report path. A host that cannot observe status/progress and
  interrupt cannot run subagent components fail-closed. A timeout, refusal,
  empty/malformed report, or nonzero/failed terminal status is a failed
  attempt. Task 7 reuses and generalizes this already-operative mapping for
  reviewer subagents; Task 5 does not depend on future prose;
- retry with a fresh prompt/report/diagnostic path, retaining the first
  attempt diagnostically but never merging it. Apply `dispatch.md`'s
  no-progress and whole-round ceilings. Record transport, resolved
  model/vendor, timeout, duration, terminal status, and attempt identity.

The rater prompt contains the sealed base/head and file inventory, subject
and ground-truth split, deployment context, the C/R anchors, and this exact
required final block:

```
RATING
C: <low|med|high|max>
C-EVIDENCE: <source locator and reason>
R: <low|med|high|max>
R-EVIDENCE: <source locator and reason>
INVENTORY:
AREA-ID: <prior ID on refresh; NEW on initial/new area>
<area> | ALIASES: <prior names or —>
       | CONSEQUENCE: <Critical|Important|Minor>
       | CONSEQUENCE-EVIDENCE: <wrong outcome + source locator>
       | GENERALIST-MISS: <evidence or —>
       | SURFACE: <canonical files/symbols/schemas/topics/keys>
       | MAPPING: resolved | ambiguous: <candidate IDs and why>
[GESTALT: +1 followed by at least three factor/evidence lines]
END-RATING
```

Anything outside the block is diagnostic. There must be **exactly one**
non-nested `RATING`/`END-RATING` pair; duplicate/nested sentinels or a
second complete block make the attempt malformed rather than letting the
parser select a favorable copy. The unique block is the parse region.
Inventory-only refreshes use the same block without C/R/GESTALT. The
adjudicator uses SKILL.md's existing pending-reprieve semantics through the
same transport and this exact parse region:

```
ADJUDICATION-PASS
EXPECTED-IDS-JSON: <minified JSON array of lexicographically sorted IDs>
<id> | DECISION: UPHOLD | BOUNCE | UNDECIDED
     | EVIDENCE: <source locator + reason>
...exactly one row per expected ID...
END-ADJUDICATION-PASS
```

Ledger/adjudication IDs are restricted to `[A-Z][A-Z0-9_-]*`; anything else
is malformed before dispatch. Example:
`EXPECTED-IDS-JSON:["L1","L2"]` (UTF-8, no spaces, JSON escaping, bytewise
lexicographic order). There must be exactly one occurrence of each
`ADJUDICATION-PASS` and `END-ADJUDICATION-PASS` sentinel, in that order and
properly paired; stray, duplicate, unmatched, reversed, or nested sentinels
are malformed. Unknown/duplicate/missing IDs, a mismatched
`EXPECTED-IDS-JSON`, absent
terminator, or an invalid decision makes the **whole pass** malformed; apply
SKILL.md's discard/retry/bounce rules atomically. `UPHOLD` keeps the proposed
reprieve, `BOUNCE` restores the row, and `UNDECIDED` triggers the one allowed
subset rerun only when the first call was clean. The hard cap is two
adjudicator calls total per round:

| Call 1 | Call 2 | Result |
|---|---|---|
| malformed/crashed | one full retry | keep final decisions from a clean retry; bounce its UNDECIDED rows without a third call, or bounce every pending row if retry malformed |
| clean with UNDECIDED | retry exactly that subset | keep call-1 final decisions; apply call-2 decisions and bounce rows still undecided/malformed |
| clean with all final | none | apply the pass |

Add CLI- and subagent-shaped adjudicator cells covering a clean
pass, a duplicate/missing-ID parse failure followed by a fresh retry, and a
second malformed pass that bounces all pending rows. Add a mixed clean pass
with final decisions plus one `UNDECIDED`: preserve the final decisions,
rerun exactly the undecided JSON ID subset, and if it remains undecided or
the subset pass fails, bounce only that subset without disturbing the kept
decisions. Add malformed call 1 → clean full retry with one UNDECIDED,
proving that row bounces without a third dispatch.

| C | Anchor |
|---|---|
| low | localized, mechanical, 1–2 files |
| med | multi-file, one subsystem, established patterns |
| high | cross-subsystem, concurrency or shared state, novel design |
| max | architectural; invariants spanning the system |

**Risk (R)** — rated **directly** on these anchors, on the same 4-point
scale as C:

| R | Anchor |
|---|---|
| low | hobby or internal, rollback easy |
| med | user-facing, recoverable |
| high | touches PII, money, authz, or data integrity; or rollback is hard |
| max | several of those at once, or irreversible exposure — non-reversible funds movement, permanent data loss, regulatory breach |

should be invented — the anchors are about blast radius and reversibility,
not severity.

```

```

**Gestalt (+1):** several sub-threshold factors can genuinely compound
past what any single one earns. A rater records:

```
GESTALT: +1
  <factor 1> — <evidence>
  <factor 2> — <evidence>
  <factor 3> — <evidence>
```

Three named factors minimum, each with its own evidence line. A genuine
gestalt can name its parts; a vibe cannot produce three citations. The
hatch only escalates — there is no downward gestalt. When a GESTALT block is

triggers a fresh retry. Never silently ignore it (under-tier) or accept it
(over-tier).

**Order of operations**, so the arithmetic is unambiguous:

```
1. merge C and R across raters (per-axis max)
2. TIER = max(C, R)
3. if min(C, R) >= high            → +1
4. if ANY rater recorded a GESTALT → +1   (once, no matter how many did)
5. cap at max
```

Gestalt applies **once after the merge**, not once per rater: two raters
both recording one still yields +1. It stacks with the step-3 bump — a
diff can legitimately earn both — and the cap absorbs the total.

Ratings, evidence, divergence flags, gestalt blocks, and the derived tier
all print in the final report. A user-passed tier overrides derivation;
the report prints both ("derived high, user pinned med").

Six findings, all verified against source before acting; two are defects Rev

1. *The renderer dispatched a truncated contract.* Rev 10's renderer takes

   declare `base_template` as `@path` or `none`, because addendum-alone and
