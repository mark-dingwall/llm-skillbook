# review-loop Tier & Roster Upgrade — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **ALSO REQUIRED:** every task that edits skill prose follows superpowers:writing-skills — RED baseline before writing, GREEN verify after. "Test" here means a pressure-scenario fixture run against a subagent, not pytest.

**Goal:** Make review-loop's roster adaptive and its cost proportionate — an effort tier derived from complexity × risk, a staffing predicate that earns each specialist, per-round re-inventory with decay, and a reviewer contract that covers absence-defined defects.

**Architecture:** All rules land inside the skill's existing forced artifacts (SCOPE seal, ROSTER, LEDGER, FIX MANIFEST, CLOSE rollup) rather than as new prose checklists — an executor that must fill a field cannot skip the rule it encodes. The tier is derived by the existing risk-inventory subagent (now run ≥2× from a config roster), combined mechanically by the orchestrator, and printed in the report. No new stage is added to the loop.

**Tech Stack:** Markdown skill documents; pressure-scenario fixtures under `tests/`; subagent dispatch for reviewers/raters/adjudicator; optional external reviewer CLIs and `multi-review` (`~/kramtime/multi-review`).

## Global Constraints

- Repo root: `~/kramtime/claude-skills` (git repository, branch `main`, initialised 2026-07-28 — see Task 0). **Two path conventions, both live:** each task's **Files** block and every `grep` are relative to `review-loop/` (the `cd` in each command establishes it); every `git add` / `git commit` runs from the repo root and therefore names `review-loop/<file>`. Both appear as written throughout — this is the convention, not a slip.
- Distillation rule (user, standing): do not bloat the skill. Rules become forced artifact fields, never prose lists. If an addition can be expressed as a field an executor must fill, express it that way.
- Ladder is exactly `low | med | high | max`. No other tier vocabulary anywhere in the docs.
- The tier may control effort **spent** (staffing threshold, round cap, reviewer model tier). It must never control what counts as **done** — `settled`, CONVERGED, merge-readiness, and the existence of the adjudication pass are tier-invariant.
- **The honest form of that claim:** the verdict *rules* are tier-invariant; the verdict *outcome* is invariant only given the same findings and the same verification quality. A cheaper tier staffs fewer areas (fewer findings, fewer rows) and audits fixes with less capable reviewers (`SKILL.md:168-173` — FIX_VERIFIED requires every reviewer's `FIX-AUDIT` line to read clean, and a weaker reviewer writes "clean" more readily). Neither is preventable; both are disclosable. Wherever the plan states the invariant, it states this qualification with it. A rule that overclaims is a rule a future editor will trust past its warrant.
- The knob gates **staffing**, never **naming**. Every inventory area is named; areas that do not earn a specialist get an explicit `Not staffed: <area> — <reason>` line. That exact field name is used everywhere — no paraphrases.
- Every rating, derivation, and staffing decision is printed in the final report with its evidence, so a run's cost is auditable after the fact.
- Two rating vocabularies exist and must never be conflated: **`CONSEQUENCE`** is `Critical | Important | Minor` (per inventory area, drives the staffing threshold) and **`R`** is `low | med | high | max` (per rater, drives the combiner). There is no mapping between them — `R` is rated directly on its own anchors, and the highest `CONSEQUENCE` in the inventory serves as `R`'s cited *evidence*, never as its value.
- **Ground truth is frozen before RED runs.** Every task's step order is: write SCENARIO → write GROUND-TRUTH (defects, scoring ladder, RED bar) → run RED → write the rule → run GREEN. Authoring the ladder after seeing RED output is retro-fitting, which is exactly what the next constraint forbids; a plan that orders the steps the other way invites it. Where the numbering below shows GROUND-TRUTH after the RED run, the numbering is wrong and this constraint governs.
- **A RED that passes invalidates its task.** Each fixture pre-commits a RED bar as a score threshold (`RED ≤ 1`), not a prediction of 0. If the current skill already scores 2, the rule is unnecessary or the fixture too easy: strengthen the fixture or drop the rule — never proceed and never retro-fit the ladder. Per `superpowers:writing-skills`, an untested rule is an unjustified rule.
- Prose edits are twin-prone: rounds 7–8 of this skill's own self-review produced three TWIN MISSES (a fixed primary statement with an unfixed sibling in another file). Every prose task runs a named twin search across `SKILL.md`, `reviewer-addendum.md`, `dispatch.md`, `DESIGN.md`, `README.md` and records the pattern + hit count.
- Fixture executor tiers: sonnet and haiku, matching `tests/baseline/RESULTS.md` convention. Score 0–2 per the scenario's ground-truth ladder. Capture rationalizations verbatim.
- **Every scenario pins the EFFORT TIER it runs under.** Staffing-dependent expectations invert across tiers: Task 3's ground truth scores 2 only when shallow areas are *unstaffed*, but at `max` the rule is that every named area is staffed, so the correct answer flips. Task 6's decay expectations are tier-sensitive the same way. Pin `TIER: <n>` in the scenario header — unpinned, a fixture silently grades against the wrong rule when Task 10 re-runs it as a regression suite. `TIER: N/A` is a legitimate value, for reviewer-side fixtures and anything whose behaviour the ladder does not touch. This binds the scenarios **this plan writes**; the three pre-existing fixture directories predate the ladder and are covered instead by Task 10's manifest, which records their real envelopes rather than assuming this one.
- **Every fixture states its prompt envelope explicitly** — the exact document set substituted into the scenario. Not "dispatch with the current skill": name the files. This is outcome-determining for Task 7, whose rules land in `dispatch.md` with only one sentence in `SKILL.md`, and for Task 5, which needs `raters.md`. A fixture given the wrong envelope fails GREEN for a reason unrelated to the rule under test, and the failure looks exactly like a real one.
- RED baseline for every fixture is the **current** skill (pre-edit), not the pre-skill draft — the question is whether today's skill already prevents the failure.

A bare memo-key bug on a ten-line diff is too findable to discriminate:
an input-hostility reviewer with nothing else to look at will stumble onto
it. The scenario therefore supplies a **decoy input surface** — visible,
attackable, and harmless — so the input-hostility reading has somewhere
plausible to spend its whole report and still attest clean.

```diff
--- a/src/pricing/discount.ts
+++ b/src/pricing/discount.ts
@@
-export function discountFor(customer: Customer, tier: Tier): number {
-  return TABLE[tier][customer.segment] ?? 0;
-}
+const memo = new Map<string, number>();
+export function discountFor(customer: Customer, tier: Tier): number {
+  const key = customer.segment;
+  const hit = memo.get(key);
+  if (hit !== undefined) return hit;
+  const value = TABLE[tier][customer.segment] ?? 0;
+  memo.set(key, value);
+  return value;
+}
@@ src/api/quote.ts
-  const qty = req.body.quantity;
+  const qty = parseInt(req.body.quantity, 10);
   const d = discountFor(customer, customer.tier);
-  return res.json({ total: price(qty) * (1 - d) });
+  return res.json({ total: price(qty) * (1 - d), discount: d });
```

The `parseInt` is the decoy: raw request input reaching arithmetic, the
shape an input-hostility reviewer is trained to circle. It must be
genuinely harmless or the ground truth is wrong, so the scenario includes
the guard that makes it so, as an accurate unchanged excerpt:

```ts
// src/api/quote.ts — route registration, untouched by this PR
router.post('/quote',
  validate({ quantity: z.number().int().max(10_000).positive() }),  // 400s before the handler
  quoteHandler);
```

**The bound is load-bearing, not decoration.** After zod, `quantity` is
already a `number`; `parseInt(n, 10)` stringifies it first, so an
unbounded contract admits values whose string form is exponential —
`1e21` becomes `"1e+21"` and parses to `1`. That is a real truncation of a
value the contract accepts, and a reviewer reporting it would be *right*
while the ground truth scores it 0. `.max(10_000)` closes it: every
accepted value has a plain decimal string form, so the parse is provably
the identity and the decoy is genuinely redundant-not-wrong.

Any future edit to this fixture that loosens the bound re-arms the trap
against the reviewer instead of the failure mode.

**Read this before editing.** `reviewer-addendum.md:5-6` instructs the
dispatcher to *"Fill `{{ }}` placeholders; resolve `[bracketed]`
sections."* Bracketed content is a menu **for the dispatcher** — it is
resolved away before the prompt reaches the reviewer, which sees only the
substituted charter string. Any definition placed inside the brackets is
therefore never read by the agent whose behaviour it is meant to change.

So the redefinition goes in **unbracketed prose** that survives
resolution, and the bracket keeps only the label list:

```markdown
## Your charter
{{ charter }}   [holistic | adversarial | specialist: <area>]

Whatever your charter, you are hostile to the claim that this diff is
correct — assume it is wrong and try to prove it. Attacking its inputs is
one way to do that, not the only one: a diff with no input boundary still
makes a correctness claim, and that claim is your target. `holistic`
scopes you to the whole review surface, `specialist` to your named area;
the posture is the same either way.
```

The `adversarial` charter is the slot where this posture is the *entire*
job rather than an overlay — which is why it stays mandatory on every
roster.

- [ ] **Step 1: Write the tier section**

Insert into `SKILL.md` between the `### SCOPE seal` section and
`### ROSTER`. Task 5 slots `### RATING` into the gap above this block, so
the finished file reads seal → RATING → EFFORT TIER → ROSTER. Do not
place this block adjacent to `### SCOPE seal` in a way that Task 5 cannot
split — leave the two as separate top-level subsections.

**Ordering matters and is easy to get backwards.** Raters skim the *sealed*
scope — that is what today's inventory subagent does (`SKILL.md:93`), and
rating an unsealed tree means rating a subject that can move underneath the
rating. But the tier cannot precede the seal either, since it is derived
*from* what the seal fixed. Correct Stage 0 order:

```
quality gate → SCOPE seal → RATING → EFFORT TIER → ROSTER
```

RATING precedes the tier because it produces the tier's inputs; the tier
precedes ROSTER because ROSTER consumes the staffing threshold. **Document
order is execution order** — a skill is read top-down by the agent running
it, so a section placed after its consumer will be applied after it too.
Task 5's insertion point and Task 8's artifact numbering must both match
this line; all three were inconsistent in Rev 1.

````markdown
### EFFORT TIER (Stage 0, after RATING, before the roster)

```
TIER: low | med | high | max
  staffing threshold : <consequence tier an area must meet to be staffed>
  round cap          : <n>
  reviewer model     : <relative tier>
  source             : user-specified | derived (see RATING)
```

| Tier | Staffing threshold | Round cap | Reviewer model |
|---|---|---|---|
| low | Critical areas only | 2 | mid-tier |
| med | Important+ | 3 | mid-tier |
| high | Important+ | 5 | one above mid |
| max | every named area | 5 | most capable |

**Threshold and decay are different mechanisms and do not override each
other.** The threshold is an *a priori* filter: it decides which areas are
eligible before anyone has reviewed anything. Decay is *evidence-based
withdrawal*: it retires an area that has been reviewed and stayed quiet.
So `max`'s "every named area" means every named area is eligible — a
decayed area at `max` is still unstaffed, because two rounds of silence is
evidence the threshold never had. Reading `max` as "decay does not apply"
would make the most expensive tier the one that can never stop staffing a
finished area, which is the opposite of what a round cap of 5 is for.

The tier controls effort **spent**. It never controls what counts as
**done**: `settled`, the CONVERGED conjuncts, merge-readiness, and the
existence of the per-round adjudication pass are identical at every tier.
A lean run finds less because it staffs less and stops sooner — never
because its bar moved. A `low` run that ends with an OPEN Important+ row
is NOT CONVERGED exactly as a `max` run would be.

Reviewer model tier applies on the subagent dispatch path (the default,
as in `superpowers:requesting-code-review`). Where a reviewer is an
external CLI or a `multi-review` fan-out, the vendor picks the model —
record what it actually ran, do not derive it. Never name model IDs in
this skill. The relative vocabulary is exactly `mid-tier`, `one above mid`
and `most capable`, resolved at dispatch against whatever the environment
offers — where it offers only two usable tiers, `one above mid` and `most
capable` resolve to the same model, which is correct, not a
misconfiguration.
Mid-tier is a floor for reviewers, never go below it: the cheapest models
take 2–3× the turns on multi-step work and cost more overall
(`superpowers:subagent-driven-development`).

The adjudicator's model is **not** on this ladder — it is set in the rater
config and overridable in the invocation, and the report prints which
model adjudicated. A cheap adjudicator weakens the anti-self-dealing
check; that should be visible, not silent.

**What a low cap costs, stated so nobody rediscovers it in the field.**
FIX_VERIFIED needs a *subsequent* round's `FIX-AUDIT` line. At cap 2, any
Important finding first raised in round 2 can be fixed but never audited,
so it ends FIX_APPLIED and the run is NOT CONVERGED. `low` therefore
converges only when round 2 surfaces nothing new at Important+. That is
the correct failure direction — it fails honest, never green — but it is a
real property: `low` is a cheap way to *find out*, not a cheap way to
*finish*. Oscillation detection needs three rounds and cannot fire at
cap 2 either.
````

- [ ] **Step 2: Add the tier line and the coverage-gap rule to CLOSE**

Two additions to the CLOSE rollup. The first is bookkeeping; the second is
the only defence against the tier's one real path to a cheaper verdict.

```markdown
- Tier line: the TIER block as resolved, its source (user-specified or
  derived), and — when derived — the full RATING derivation chain,
  including any `RATING-DIVERGENT` flag and which model adjudicated. A
  reader must be able to see why this run cost what it cost.
- **Coverage gaps**: every area the inventory named at Important+
  CONSEQUENCE that **no round ever staffed**, with its recorded reason,
  aggregated across the whole loop. These are **known blockers in the
  merge-readiness verdict**, listed exactly as BACKLOGGED Important+ rows
  are.
- **Decayed after coverage**: every Important+ area that *was* staffed for
  at least one round and later decayed, with the round it decayed in.
  Reported, **not** a blocker.
```

The split is the whole point of the field. "Unstaffed in any round" would
sweep both together and make a well-reviewed area that went quiet — the
exact outcome decay is designed to produce — permanently block the merge,
so the only way to a merge-ready `max` run would be to defeat decay. The
epistemics differ: a never-staffed area is an unexamined risk, which is
what makes it BACKLOGGED-equivalent; a decayed one was examined, found
clean twice, and is disclosed so a reader can see where attention stopped.

The reasoning matters more than the rule. A staffing threshold cannot
lower the bar directly — but an unstaffed area produces no findings, no
findings produce no ledger rows, and the CONVERGED test only inspects rows
that exist. So a cheap tier reaches green by never looking, and no grep
over the verdict rules can see it happen.

That is not preventable, only disclosable. An unstaffed Important+ area is
epistemically identical to a BACKLOGGED Important+ row — a known,
unexamined risk — and `SKILL.md:279-283` already has the machinery:
*"NOT merge-ready while any BACKLOGGED or factual-UNVERIFIABLE Important+
row exists; list each as a known blocker."* Reuse it rather than inventing
a parallel mechanism.

The rule is uniform across tiers, so the verdict stays tier-independent —
at `max` it is a no-op because nothing goes unstaffed. What changes is
that the tier's purchase appears on the receipt: "converged, not
merge-ready, 3 areas unreviewed at low tier" is an honest and useful
outcome. "Converged" alone would not be.

- [ ] **Step 1: Write the rater config convention**

Create `raters.md`:

````markdown
# Rater configuration

Raters skim the sealed scope and return the risk-surface inventory plus a
complexity rating. Their output derives the EFFORT TIER when the user did
not pass one.

**At least two raters run, from different vendors where available.** The
derivation is the highest-leverage step in the loop; a single rater's
miss compounds through staffing, rounds, and model choice for every
subsequent round. Two independent inventories also give free double
coverage of the risk surface itself.

**What two raters actually buy, stated honestly.** Across different
vendors, this is genuine independence: different training, different
blind spots. In a subagent-only environment — the default dispatch path —
two raters are two samples of one model. That reduces sampling variance
and catches careless reads; it does **not** defend against a systematic,
model-shaped blind spot, and nobody should believe it does. The cost is
paid on every run, including runs that turn out to be `low`, because the
tier is unknown until rating completes. Worth it for the variance
reduction alone; do not oversell it.

Raters are listed in a config file. If no config exists, **ask** — never
invent a rater command, exactly as `SKILL.md:134` already requires for
reviewer commands. `--force` skips the prompt and runs the **fallback
rater** defined below, matching the existing `--force` semantics for the
>8-reviewer confirmation gate. `--force` means one thing throughout the
skill — *proceed without asking, wherever the skill would ask* — and every
place it applies records what it bypassed; here the report carries
`RATING: fallback single rater (--force)` so the weaker derivation is
visible in the artifact rather than silent.

Each entry declares how it is dispatched, because "claude" alone does not
say whether to spawn a subagent or shell out, and the two have different
failure modes:

```yaml
# review-loop-raters.yaml
raters:
  - name: claude
    kind: subagent            # subagent | cli
    model: most-capable       # relative tier, resolved at dispatch; never a model ID
  - name: codex
    kind: cli
    command: codex exec       # the invocation, verbatim, as the user runs it
  - name: kimi
    kind: cli
    command: kimi --print

adjudicator:                  # per-round adjudication pass
  kind: subagent
  model: most-capable

fallback:                     # used only under --force with no config
  kind: subagent
  model: most-capable
```

**Field meanings, so nothing is left to inference.** `kind: subagent`
dispatches in-session and `model` names a *relative* tier from the EFFORT
TIER vocabulary (`mid-tier`, `one above mid`, `most capable`) — never a
model ID, per the no-hardcoded-models rule. `kind: cli` shells out and
`command` is the invocation verbatim; the vendor picks the model, so
`model` is ignored and what actually ran is recorded from the CLI's own
report. A CLI rater that exits non-zero or returns an unparseable rating
is a failed rater, not a zero — drop it, note it, and if that leaves fewer
than two, say so in the report rather than deriving from one in silence.

`most-capable` is the default for raters and the adjudicator alike, and
deliberately not on the effort ladder: these run once per loop (raters) or
once per round (adjudicator) against reviewers that run several times each,
so the saving from cheapening them is small and the compounding cost of
getting them wrong is not.

Leaderboard positions change frequently; this file is expected to be
edited often. Nothing in the skill hardcodes a vendor or a model ID.

### RATING (Stage 0, after the seal, before the tier)

Raters come from the rater config ([raters.md](raters.md)) — at least two,
different vendors where available. Each returns the risk-surface inventory
**and** a complexity rating. Forced choice from the anchors; no other
vocabulary; between two anchors, pick the higher.

**RATING always runs, including when the user passed a tier.** The raters
are the only thing that produces the risk-surface inventory, and ROSTER
cannot staff areas that were never named — skipping RATING on a pinned
tier would leave Stage 0 with a threshold and nothing to apply it to. The
derivation is cheap relative to the reviewers it sizes, and running it
unconditionally is what makes the report able to say *"derived high, user
pinned med"*: a pinned tier **overrides** the derived one, it does not
suppress it. A pin that lands two or more steps below the derivation is
worth a line in the report saying so — the user is entitled to make that
call, and equally entitled to see it recorded.

**Complexity (C)** — observable proxies, language-agnostic:

| C | Anchor |
|---|---|
| low | localized, mechanical, 1–2 files |
| med | multi-file, one subsystem, established patterns |
| high | cross-subsystem, concurrency or shared state, novel design |
| max | architectural; invariants spanning the system |

**Risk (R)** — rated **directly** on these anchors, on the same 4-point
scale as C:

| R | Anchor |
|---|---|
| low | hobby or internal, rollback easy |
| med | user-facing, recoverable |
| high | touches PII, money, authz, or data integrity; or rollback is hard |
| max | several of those at once, or irreversible — funds movement, data loss, regulatory exposure |

`R` is **not** derived from the inventory's `CONSEQUENCE` field. The two
are different scales measuring different things: `CONSEQUENCE` is
`Critical | Important | Minor` and answers "how bad is a defect *in this
area*", driving the per-area staffing binary; `R` is
`low | med | high | max` and answers "what does this change put at risk
overall", driving the combiner. There is no function between them and none
should be invented — the anchors are about blast radius and reversibility,
not severity.

They do connect, as evidence: the highest-`CONSEQUENCE` area in the
inventory is normally what a rater cites to justify its `R`. Cited, not
computed.

Each rating cites **one line of evidence** — the file or area that drove
it. An uncited rating is not usable; re-run that rater.

**Merge across raters:** per-axis maximum. A spread of ≥2 steps on either
axis takes the higher value and records `RATING-DIVERGENT` with both
raters' evidence lines — a 2-step spread on a 4-point scale means the
scope itself is ambiguous, which is worth surfacing.
`--escalate-divergence` on the invocation makes a divergence stop and ask
the user instead of resolving it upward.

**Inventories merge as the union of areas, carrying the whole record.**
For an area both raters named, take the highest `CONSEQUENCE` stated and
keep **both** `GENERALIST-MISS` lines. Merging on consequence alone would
drop `GENERALIST-MISS`, and an area that cannot state it does not earn a
specialist — so a lossy merge silently unstaffs areas that both raters
justified. Two different accounts of why a generalist would miss an area
are two reasons, not a contradiction to be resolved; the specialist's
charter is better for having both.

**Combiner:**

```
TIER = max(C, R), then +1 step if min(C, R) >= high, capped at max
```

**Gestalt (+1):** several sub-threshold factors can genuinely compound
past what any single one earns. A rater records:

```
GESTALT: +1
  <factor 1> — <evidence>
  <factor 2> — <evidence>
  <factor 3> — <evidence>
```

Three named factors minimum, each with its own evidence line. A genuine
gestalt can name its parts; a vibe cannot produce three citations. The
hatch only escalates — there is no downward gestalt.

**Order of operations**, so the arithmetic is unambiguous:

```
1. merge C and R across raters (per-axis max)
2. TIER = max(C, R)
3. if min(C, R) >= high            → +1
4. if ANY rater recorded a GESTALT → +1   (once, no matter how many did)
5. cap at max
```

Gestalt applies **once after the merge**, not once per rater: two raters
both recording one still yields +1. It stacks with the step-3 bump — a
diff can legitimately earn both — and the cap absorbs the total.

Ratings, evidence, divergence flags, gestalt blocks, and the derived tier
all print in the final report. A user-passed tier overrides derivation;
the report prints both ("derived high, user pinned med").
````

## multi-review as the holistic slot

`--multi-review-rounds N` (default off) routes the **holistic** slot
through `multi-review` for the first N rounds — the fan-out earns its cost
on round 1's full surface and stops earning it once rounds are reviewing a
small fix diff. It occupies exactly one roster slot; its synthesizer
produces the single consolidated report that slot's completion contract is
judged against.

Five constraints, each of which voids or corrupts the round if missed:

- **Run it from a working directory outside the sealed tree**, with
  absolute paths in `files` and `context_files`, and `output_dir` external
  too. `output_dir` alone is not enough: multi-review's aggregate step
  writes `REVIEW-<slug>.md` to **cwd root** (`skills/multi-review/SKILL.md`
  §Step 7), and paired mode promotes the staged session dir to cwd root as
  well. Invoked from the repo under review, it writes into the sealed tree
  no matter where `output_dir` points, and an in-tree loop artifact voids
  its own round.
- **Pin `reviewers` to a contained set.** Two reasons, and the second is
  the serious one. First, `pykrete` and `agy` are default-on and appear as
  failed sections until configured, so an unpinned set trips the
  fail-closed rule every round on a reviewer nobody chose. Second,
  multi-review's own `CLAUDE.md` documents both as *agentic and
  uncontained* — `agy --print` was observed running `pytest` and grepping
  the repo unprompted, and pykrete wraps the same posture. A reviewer that
  can execute commands in the working tree cannot be given the sealed
  tree, and its own docs say not to point it at code you have not
  vouched for. The `claude` reviewer agent is restricted to `Read`,
  `Grep`, `Glob` with no `Bash`, which is what a review-loop reviewer's
  read-only contract requires. Anything outside that allowlist needs the
  bwrap/`--sandbox` containment on multi-review's backlog first.
- **`mode: reference`**, not inline. Reviewers must run the diff command
  and read enclosing functions with their own tools. `files` is the
  SUBJECT set; `context_files` is GROUND TRUTH.
- **The reviewer's contract arrives via `custom_prompt`.** review-loop's
  reviewer prompt — the superpowers template plus `reviewer-addendum.md`
  with `{{ }}` filled and `[brackets]` resolved, charter `holistic` — is
  passed there in full. Without it there is no evidence contract, no
  severity vocabulary, no charter attestation and no `FIX-AUDIT` lines, so
  the harvest below has nothing to check for and the slot's completion
  contract is unenforceable. multi-review appends `custom_prompt` to its
  task preset rather than replacing it (filed on its backlog 2026-07-28);
  verify that is still true at execution time, because a replacing
  implementation would drop the addendum's read-only clause.
- **Harvest the raw per-reviewer sections; treat the synthesis as a
  convenience.** `REVIEW.md`'s per-reviewer sections are the authoritative
  input to triage. The synthesis cannot be, and the reason is structural:
  its template (`agents/multi-review-synthesizer.md`) offers **Agreed
  Concerns** — items multiple reviewers raised — and **Divergent Views**,
  scoped to *"item where reviewers disagree"*. A concern one reviewer
  raised and no one contradicted fits neither heading, and a lone
  reviewer's finding is exactly the signal a fan-out is bought for. Read
  every healthy section, carry each distinct concern into triage with the
  reviewer that raised it, and use the synthesis to see where reviewers
  converged — not to decide what exists.

**Completion is judged against the per-section roster, not the synthesis.**
A dead section inside an otherwise-clean consensus is exactly the
NOT RUN ≠ clean hole. Any failed section fails the slot: retry once, then
INDETERMINATE. Charter attestation is required per section and checked at
harvest — the synthesis has no attestation to inherit.

The synthesizer **consolidates; it does not adjudicate**. It reads the
reviews, never the sources. review-loop's adjudication pass is unaffected
and still required.
