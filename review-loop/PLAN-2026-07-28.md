# review-loop Tier & Roster Upgrade — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **ALSO REQUIRED:** every task that edits skill prose follows superpowers:writing-skills — RED baseline before writing, GREEN verify after. "Test" here means a pressure-scenario fixture run against a subagent, not pytest.

**Goal:** Make review-loop's roster adaptive and its cost proportionate — an effort tier derived from complexity × risk, a staffing predicate that earns each specialist, per-round re-inventory with decay, and a reviewer contract that covers absence-defined defects.

**Architecture:** All rules land inside the skill's existing forced artifacts (SCOPE seal, ROSTER, LEDGER, FIX MANIFEST, CLOSE rollup) rather than as new prose checklists — an executor that must fill a field cannot skip the rule it encodes. The tier is derived by the existing risk-inventory subagent (now run ≥2× from a config roster), combined mechanically by the orchestrator, and printed in the report. No new stage is added to the loop.

**Tech Stack:** Markdown skill documents; pressure-scenario fixtures under `tests/`; subagent dispatch for reviewers/raters/adjudicator; optional external reviewer CLIs and `multi-review` (`~/kramtime/multi-review`).

## Global Constraints

- Repo root: `~/kramtime/claude-skills` (git repository, branch `main`, initialised 2026-07-28 — see Task 0). All paths in this plan are relative to that root; the skill's own files live under `review-loop/`.
- Distillation rule (user, standing): do not bloat the skill. Rules become forced artifact fields, never prose lists. If an addition can be expressed as a field an executor must fill, express it that way.
- Ladder is exactly `low | med | high | max`. No other tier vocabulary anywhere in the docs.
- The tier may control effort **spent** (staffing threshold, round cap, reviewer model tier). It must never control what counts as **done** — `settled`, CONVERGED, merge-readiness, and the existence of the adjudication pass are tier-invariant.
- The knob gates **staffing**, never **naming**. Every inventory area is named; areas that do not earn a specialist get an explicit `not staffed because <reason>` line.
- Every rating, derivation, and staffing decision is printed in the final report with its evidence, so a run's cost is auditable after the fact.
- Prose edits are twin-prone: rounds 7–8 of this skill's own self-review produced three TWIN MISSES (a fixed primary statement with an unfixed sibling in another file). Every prose task runs a named twin search across `SKILL.md`, `reviewer-addendum.md`, `dispatch.md`, `DESIGN.md`, `README.md` and records the pattern + hit count.
- Fixture executor tiers: sonnet and haiku, matching `tests/baseline/RESULTS.md` convention. Score 0–2 per the scenario's ground-truth ladder. Capture rationalizations verbatim.
- RED baseline for every fixture is the **current** skill (pre-edit), not the pre-skill draft — the question is whether today's skill already prevents the failure.

````markdown
### EFFORT TIER (Stage 0, before the seal)

```
TIER: low | med | high | max
  staffing threshold : <consequence tier an area must meet to be staffed>
  round cap          : <n>
  reviewer model     : <relative tier>
  source             : user-specified | derived (see RATING)

| Tier | Staffing threshold | Round cap | Reviewer model |
|---|---|---|---|
| low | Critical areas only | 2 | mid-tier |
| med | Important+ | 3 | mid-tier |
| high | Important+ | 5 | one above mid |
| max | every named area | 5 | most capable |

The tier controls effort **spent**. It never controls what counts as
**done**: `settled`, the CONVERGED conjuncts, merge-readiness, and the
existence of the per-round adjudication pass are identical at every tier.
A lean run finds less because it staffs less and stops sooner — never
because its bar moved. A `low` run that ends with an OPEN Important+ row
is NOT CONVERGED exactly as a `max` run would be.

Reviewer model tier applies on the subagent dispatch path (the default,
as in `superpowers:requesting-code-review`). Where a reviewer is an
external CLI or a `multi-review` fan-out, the vendor picks the model —
record what it actually ran, do not derive it. Never name model IDs in
this skill; "mid-tier", "most capable" resolve at dispatch time.
Mid-tier is a floor for reviewers, never go below it: the cheapest models
take 2–3× the turns on multi-step work and cost more overall
(`superpowers:subagent-driven-development`).

The adjudicator's model is **not** on this ladder — it is set in the rater
config and overridable in the invocation, and the report prints which
model adjudicated. A cheap adjudicator weakens the anti-self-dealing
check; that should be visible, not silent.
````

**Why:** this is the step with the most leverage in the whole skill — a mis-derived tier compounds through staffing, rounds, and model choice for the entire run. Hence ≥2 independent raters and a mechanical combiner rather than a single judgment call.

- [ ] **Step 1: Write the rater config convention**

Create `raters.md`:

````markdown
# Rater configuration

Raters skim the sealed scope and return the risk-surface inventory plus a
complexity rating. Their output derives the EFFORT TIER when the user did
not pass one.

**At least two raters run, from different vendors where available.** The
derivation is the highest-leverage step in the loop; a single rater's
miss compounds through staffing, rounds, and model choice for every
subsequent round. Two independent inventories also give free double
coverage of the risk surface itself.

Raters are listed in a config file. If no config exists and the user did
not pass a tier, **ask** — never invent a rater command, exactly as with
reviewer commands.

```yaml
# review-loop-raters.yaml
raters:
  - claude          # subagent or CLI, per the user's environment
  - codex
  - kimi
adjudicator: claude # model/CLI for the per-round adjudication pass
```

Leaderboard positions change frequently; this file is expected to be
edited often. Nothing in the skill hardcodes a vendor.

## Worked example

Two raters return:

| Rater | C | R (highest consequence in its inventory) |
|---|---|---|
| claude | high | high |
| codex | med | high |

Per-axis max → C = high, R = high. Combiner: `max(high, high)` = high;
`min(C,R)` = high ≥ high, so +1 → **max**. Spread on the C axis is one
step, below the divergence threshold, so no flag.
````

- [ ] **Step 2: Write the RATING section**

Insert into `SKILL.md` after the EFFORT TIER block:

````markdown
### RATING (Stage 0, only when the user did not pass a tier)

Raters come from the rater config ([raters.md](raters.md)) — at least two,
different vendors where available. Each returns the risk-surface inventory
**and** a complexity rating. Forced choice from the anchors; no other
vocabulary; between two anchors, pick the higher.

**Complexity (C)** — observable proxies, language-agnostic:

| C | Anchor |
|---|---|
| low | localized, mechanical, 1–2 files |
| med | multi-file, one subsystem, established patterns |
| high | cross-subsystem, concurrency or shared state, novel design |
| max | architectural; invariants spanning the system |

**Risk (R)** = the highest `CONSEQUENCE` named in that rater's inventory,
mapped to:

| R | Anchor |
|---|---|
| low | hobby or internal, rollback easy |
| med | user-facing, recoverable |
| high | touches PII, money, authz, or data integrity; or rollback is hard |
| max | several of those at once, or irreversible — funds movement, data loss, regulatory exposure |

Each rating cites **one line of evidence** — the file or area that drove
it. An uncited rating is not usable; re-run that rater.

**Merge across raters:** per-axis maximum. A spread of ≥2 steps on either
axis takes the higher value and records `RATING-DIVERGENT` with both
raters' evidence lines — a 2-step spread on a 4-point scale means the
scope itself is ambiguous, which is worth surfacing. When the invocation
passes the escalate flag, a divergence stops and asks the user instead.
Inventories merge as the union of areas, taking the highest consequence
stated for each.

**Combiner:**

```
TIER = max(C, R), then +1 step if min(C, R) >= high, capped at max
```

**Gestalt (+1, at most once):** several sub-threshold factors can
genuinely compound past what any single one earns. A rater may bump one
step by recording:

```
GESTALT: +1
````

- [ ] **Step 2: Write the multi-review section**

Add to `dispatch.md`:

````markdown
## multi-review as the holistic slot

`--multi-review-rounds N` (default off) routes the **holistic** slot
through `multi-review` for the first N rounds — the fan-out earns its cost
on round 1's full surface and stops earning it once rounds are reviewing a
small fix diff. It occupies exactly one roster slot; its synthesizer
produces the single consolidated report that slot's completion contract is
judged against.

Four constraints, each of which voids or corrupts the round if missed:

- **`output_dir` must point outside the sealed tree.** Its default is
  `<cwd>/.multi-review/sessions/<slug>/` — in-tree, and an in-tree loop
  artifact voids its own round.
- **Pin `reviewers` explicitly.** `pykrete` and `agy` are default-on and
  appear as failed sections until configured — an unpinned set trips the
  fail-closed rule every round on a reviewer nobody chose.
- **`mode: reference`**, not inline. Reviewers must run the diff command
  and read enclosing functions with their own tools. `files` is the
  SUBJECT set; `context_files` is GROUND TRUTH.
- **Harvest Agreed Concerns AND Divergent Views.** A finding only one
  reviewer raised is a candidate ledger row, not noise — triage decides
  its fate, not the synthesizer. The synthesizer cites which reviewer
  raised each item, so provenance survives the merge.

**Completion is judged against the per-section roster, not the synthesis.**
A dead section inside an otherwise-clean consensus is exactly the
NOT RUN ≠ clean hole. Any failed section fails the slot: retry once, then
INDETERMINATE. Charter attestation is required per section and checked at
harvest — the synthesis has no attestation to inherit.

The synthesizer **consolidates; it does not adjudicate**. It reads the
reviews, never the sources. review-loop's adjudication pass is unaffected
and still required.
````
